# Writing Notes

本文件用來記錄「可重用的文章骨架」、「值得保留的寫作技巧」與「值得逆向拆解的優秀文章」。目標不是把寫作模板鎖死，而是留下作者自己之後會回頭看的 writing notes，讓起稿時不必每次都從零發明章節順序，也能逐步沉澱哪些寫法真的能幫讀者建立判斷力。

## 使用方式

- 先選「這篇文章要幫讀者完成什麼」：理解一個觀點、學會一個流程、比較兩個選項、吸收一批研究、或整理自己的思考。
- 起稿前先訂一條 `NarrativeArc`（敘事與論證弧線）：這篇準備用什麼推理路徑把讀者帶到結論。之後每一段、每個 `block`、每個 `callout` 都可以回頭檢查是否仍在主線上。
- 再選最接近的骨架：不要求逐段照抄，但至少先有一個 baseline。
- 若之後看到很喜歡的文章，可隨時把它補進本文件的「參考文章」或新增一種模板；這份文件預設就是可擴充的，不是一次性定稿。
- 不把這份文件視為 parser/template spec；它先是寫作設計文件。未來若某些骨架穩定到值得產品化，再考慮變成 `tools/create_content.py` 模板。

## 統一的 `<draft>` 骨架

每篇 source 的 `<draft>` 先列三個必填規劃欄位，再接文章專屬的章節骨架；確有後續篇目才加 `FollowUps`。這是作者的工作區，不是讀者可見的導讀：

1. `TLDR`：用 1–3 句指出本文最主要的主軸與可帶走的判斷，不只複述題名。
2. `NarrativeArc`：概括讀者從問題、直覺、機制、證據到結論的**敘事與論證路徑**，交代為何按這個順序走；比 `MainFlow` 更準確地表達文章的推進。
3. `Scope`：正面界定本篇聚焦的問題、材料與推論深度；必要的邊界直接寫在這裡，不另列 `OutOfScope`。
4. `FollowUps`（選填）：確有可延伸的獨立問題或篇目時才列，不能用它代替本篇應有的結論。

這些欄位之後空一行，直接列章節骨架。**章節一律用 `- 段落角色｜核心主張：內容`**：`｜` 分開段落角色與這一節要說的事，`：` 引出具體內容。寫 `- 前情提要｜為何需要召回：...`，不寫 `- 前情提要：...`，也不在清單標記後再寫 `1.`、`2.`。縮排子項用四格空白加 `-`；確有先後順序的子清單才用 `1.`、`2.`。不要只放抽象章名，或另起沒有清單標記的獨立行。**當一組縮排子項結束、下一個非縮排的同級項目開始時，兩者之間空一行**，讓章節界線一眼可見。起稿時先填這些欄位，通常能更早發現：

- 這篇到底是在做 overview，還是在做單一方法 deep dive
- 文章是不是同時想講太多件事
- limitation / comparison / related work 是否已經偏離主 flow

## Draft 骨架編寫規範（Authoring Scaffolding）

起稿或建立新文章時，應優先在 source `.md` 頂部的 `<draft>...</draft>` 區塊內保留整篇文章的結構骨架與核心內容構想。`<draft>` 屬於作者專屬的 planning scaffolding，不會進入公開渲染的 HTML，也不會進入全站搜尋索引。

### 把 `<draft>` 寫成可接續的推理地圖

對照已發布的 `Semantic ID`、`RQ-Kmeans` 與《結果偏誤》可看出，好的 `<draft>` 不只列「背景／方法／限制」幾個章名，而會留下**為什麼這一節必須接在上一節後面**。`RQ-Kmeans` 從「連續向量如何變 Token」走到網格分桶的困境，再引出 VQ、殘差量化與死碼；《結果偏誤》除了章節，還保存了引子、反例、素材與結尾要回扣的問題。`Semantic ID` 的草稿也記下分類樹類比哪裡失準、準備用什麼新比喻替換。這些都是日後重寫時真正有用的資訊。

實務上先寫上方的規劃欄位，再為每個主要章節補推理線索。第一個敘事章節用 `開頭：` 引入讀者當下的問題；中段用 `承先：` 回應上一節留下的問題，並用 `啟後：` 提出下一節要解的問題；最後一個敘事章節用 `結尾：` 回扣主線。`證據：` 標明支撐材料及其可證明的範圍，沒有具體材料時不硬加。這些是寫作功能標記，不必讓正文出現同樣字眼；英文 source 使用 `Opening / BuildsOn / Next / Closing / Evidence`，章節仍用 `｜` 分隔角色與主張。參考文獻等附錄不必硬寫成結尾。其他子項可保留例子、反例與待核對問題，但至少讓下一次接手的人知道推理如何往前走：

1. **讀者此刻知道什麼、還缺什麼**：本節要先補哪個直覺、情境或前提？
2. **本節要推出什麼**：一句可檢驗的核心主張，以及讓它成立的原因；避免只寫一個抽象題名。
3. **用什麼支撐**：具體例子、反例、公式、來源或自己的觀察；標清「已公開的證據」「尚待核對的假說」與「只供作者參考的素材」。
4. **怎麼啟後**：本節回答後自然留下什麼問題？用這個問題安排章節順序，避免各段變成獨立卡片。
5. **邊界與取捨**：哪個常見誤解要校準、哪個推論不能由現有證據推出、哪些細節要留給別篇？

例如寫一篇方法的限制，不要只在草稿裡列「限制一／二／三」。先記下方法解決了哪個痛點、又引進了哪個新前提；每項限制應從前一個設計選擇自然長出來。正文可以比 `<draft>` 精簡，也可以調整順序；修改正文後，應回頭更新已過期的草稿骨架，避免它變成另一份與文章相矛盾的摘要。

### 統一格式範例

同一套欄位適用於 `notes/` 與 `writing/`；章節名稱與子項依文章而定。下面示範章節的主張、支撐材料與承先啟後如何相接：

```markdown
<draft>
- TLDR：好決策可能得到壞結果；評估選擇應回到當時資訊與決策過程。
- NarrativeArc：由事後懊悔辨認結果偏誤，再用不完全資訊與機率拆開決策品質和單次結果，最後提出長期校準的方法。
- Scope：聚焦結果偏誤與有限資訊下的個人決策評估。
- FollowUps：若要深入，可另寫機率校準與決策紀錄。

- 引子｜一次令人後悔的選擇：先呈現「當時已盡力，結果卻不如預期」的情境，讓讀者看見要解釋的落差。
    - 開頭：用一個高勝率選擇失敗的情境提出問題。
    - 例子：原本勝率高的路徑仍可能落在小機率的壞結局。
    - 啟後：結果不好，是否就能倒推當初決策錯誤？

- 結果偏誤｜區分決策品質與結果：定義以成敗倒推選擇的偏誤，再說明當時資訊有限、結果也受隨機性影響。
    - 承先：回應開頭的自責，先拆開當時的選擇與事後的結果。
    - 反例：僥倖成功的壞決策，不應只因成功就被複製。
    - 啟後：若單次結果不能評價決策，該用什麼標準？

- 收束｜回到當時資訊與長期過程：用可得證據、事前預測與反覆實踐檢查方法，而非用一次輸贏定義自己。
    - 承先：前節已分開決策與結果，現在需要可實踐的評估標準。
    - 結尾：回扣開頭的遺憾，提醒讀者用長期過程校準判斷。
</draft>
```

若沒有具體後續問題，省略 `FollowUps`。已有豐富草稿時可保留更多層級的例子與論證材料；同級項目之間的空行規則照用。英文文章用英文寫內容，規劃欄位名維持相同。

## 前段導讀 Block

如果文章前段想放一個可見的導讀 block，我現在更偏好把它收斂成：

- 這篇最重要的主題是什麼
- 這篇會怎麼走（`NarrativeArc`）
- 這篇聚焦的問題與深度（`Scope`）

而不是再另外做一個專門的 `Guiding Questions` 特殊區塊。原因是：

- 你本來就常把 guiding questions 分散在各段的 opening 與轉場裡
- 若前面再開一個 `Guiding Questions` block，容易變成重複
- 真正更需要被 upfront 固定下來的，反而是這篇的焦點、範圍與理解路徑

命名上可先把它理解成 `TL;DR`，但語意更接近：

- `Focus`
- `Article Compass`
- `This article focuses on...`

重點不是名字，而是它的責任：幫讀者在一開始就抓住主線。

## Overview vs Deep Dive

知識型文章最容易 overloaded 的情況，是把「介紹一個主題家族」和「完整講完其中幾個方法」硬塞在同一篇。

- 若主問題是「Clustering 是什麼、為什麼重要、有哪些主要路線、它們差在哪」，那這篇應該是 overview
- 若主問題是「K-Means 到底怎麼運作、它的假設與 limitation 是什麼」，那這篇應該是 single-method deep dive
- 若主問題是「DBSCAN 何時比 K-Means 更自然」，那這篇更接近 comparison / decision guide

實務上可優先拆成兩層：

- overview 頁：建立方法地圖、主要差異軸、適用情境與後續閱讀路線
- follow-up 頁：各自處理 `K-Means`、`DBSCAN`、`Hierarchical Clustering`、`AGNES`、`DIANA`、`HDBSCAN` 等單一方法

對 overview 頁來說，更重要的是：

- 先把讀者帶到「這個方法家族在解什麼問題」
- 再把主要分支與差異軸講清楚
- 最後把各方法留待後續頁面深挖
- 若必須提到某個代表方法，也應以「用它定位這一類方法的角色」為主，而不是讓整篇重心被它的直覺、推導或 step-by-step 機制綁走

這樣做的好處不只是 flow 比較乾淨，也比較好 scale：

- 之後可以更自然地把更多相關方法放進 overview（例如 `Hierarchical Clustering`、`AGNES`、`DIANA`、`HDBSCAN`）
- overview 不需要每新增一個方法就再長出一大段 deep dive，結構比較穩
- 單一方法頁可以各自擴充 intuition、limitation、tuning 與 comparison，而不會把總覽頁撐爆

而不是在同一篇裡同時塞滿：

- 方法家族背景
- 單一演算法機制
- 每個演算法各自的 limitation
- tuning 細節
- 全量 comparison

## Reverse Engineering 流程

當遇到一篇想學的文章時，優先記以下欄位：

1. 開頭怎麼 hook 讀者？
2. 它先給結論，還是先鋪背景？
3. 主體是按什麼邏輯展開：時間、問題、步驟、比較維度、還是抽象層級？
4. 哪些段落是「必要骨架」，哪些只是作者自己的材料？
5. 結尾做的是總結、升維、CTA，還是留一個更大的問題？

記完後，再把它歸到下列模板之一；若放不進去，就新增一種模板。

## 寫作技巧

### 1. 理論去神聖化

- 適合：文章需要引用理論、框架、最佳實踐或經典說法，但你不想把它們寫成不可違背的標準答案。
- 核心寫法：先交代理論上的典型說法，再補一句真實情境中通常會怎麼調整、折衷或偏離。
- 目的：幫讀者建立的是判斷力，而不是僵化照抄的 reflex。
- 常見句型：
  1. `理論上...；但實際上...`
  2. `標準教科書會這樣切；不過在真實工作裡，常常會因為...而改成...`
  3. `這個框架很有用，但更重要的是知道它在哪些情況下會失真`
- 使用提醒：
  - 不要把「實務上會調整」寫成反智地否定理論；重點是讓理論回到可用框架，而不是把理論整個拆掉。
  - 最好補出 adjustment 的條件，說清楚是什麼 constraint、目標或現場訊號，讓作者做出偏離。
  - 若文章在教方法，這種寫法通常比直接背最佳實踐更能幫讀者形成 decision logic。
- 例子：
  - `理論上應先完整定義問題再選方法；但實際上很多時候你只能先用粗略假設開局，再邊做邊收斂問題。`

### 2. 階層化鷹架與零割裂知識堆疊（Layered Scaffolding & Anti-Fracture Flow）

- **適合**：所有知識型文章、技術筆記、架構演進剖析，以及需要傳遞複雜認知模型的長文。
- **核心心智哲學**：
  - 讀者的工作記憶（Working Memory）容量極為有限。許多技術文章之所以讓人讀起來「滿滿割裂感」、「學一學大腦斷線」，根本原因在於作者在行文中犯了**「隱性跳步」**——底層基礎還沒交代完整，就突兀拋出高階機制或切換到另一維度，讀者腳下沒有認知支點，心智模型被迫懸空。
  - 真正具備極高可讀性、流暢自如的文章，必然像**「砌磚蓋樓」**一樣：**底層的一批磚必須先平鋪整齊、形成堅實平臺；讀者在這個平臺上站穩後，再往上堆第二層磚，然後再向上收斂到頂層**。
- **三層鷹架架構（The 3-Layer Pedagogical Scaffolding）**：
  1. **Layer 1: 底層基石群（Base / Intuition / Constraint Layer）**：
     - **涵蓋內容**：日常生活直覺、具體業務/物理痛點、輸入約束條件、底層先備特徵。
     - **成群原則（Clustered Foundation）**：同一個認知層級的線索必須「成批鋪齊」。例如要講一個複雜演算法，先將其面對的「問題背景、物理天花板、傳統直覺的破滅」在底層交代完整，絕不允許「先講痛點 A $\to$ 突兀跳到高階算法 X $\to$ 回頭又補痛點 B」。
  2. **Layer 2: 中階機制與引理推導（Intermediate Mechanism & Lemma Layer）**：
     - **涵蓋內容**：由底層約束自然碰撞、推理衍生的核心概念、關鍵解法流程、中階抽象（Intermediate Lemma）。
     - **因果承托**：每一個中階機制的引入，都必須能精準對應到 Layer 1 中的具體線索，讓讀者感受到「為了解決剛才那個痛點，自然會長出這個解法」，而不是天外飛來一筆。
  3. **Layer 3: 高階架構、極限挑戰與升維結論（High-Level Architecture & Synthesis Layer）**：
     - **涵蓋內容**：全域系統架構組合、極端場景（Corner Cases / Failure Modes）、深水區防禦機制、全局 Trade-offs 與認知升維。
     - **穩固著陸**：頂層的高深結論必須完全坐落在前兩層的推演之上。讀者抵達此處時，會產生「水到渠成、豁然開朗」的閱讀快感。
- **三大割裂反模式與避坑原則（Anti-Patterns & Remedies）**：
  1. **反模式一：空中樓閣（Unbacked Leap）**
     - *現象*：前文未鋪墊底層概念，突然空降高階專有名詞或複雜機制（例如在未解釋「何謂向量空間中的殘差」之前，就直接講「RQ 殘差量化碼本」）。
     - *修正*：退回底層，先用生活比喻或幾何直覺補齊該概念的基石，再向上引導。
  2. **反模式二：板塊孤島拼貼（Fractured Islands）**
     - *現象*：段落 A 講完一個點，段落 B 突然切換到另一個點，兩段都在講同一個大主題，但中間毫無因果過渡，像各自獨立的摘要卡拼湊。
     - *修正*：建立段落間的「因果接力棒（Causal Handover）」——以問題驅動轉場（如「既然傳統方案在上述約束下撞牆，我們該如何破局？」），拉著讀者順流而下。
  3. **反模式三：概念倒置（Inverted Explanation）**
     - *現象*：試圖用更抽象、更複雜的數學符號或高階理論，去解釋本來就很簡單的低階直覺。
     - *修正*：嚴格遵守「先直覺、再抽象、再正式定義」的節奏。
- **文章流暢度自檢清單（The Cohesion Checklist）**：
  - [ ] 讀者在閱讀當前段落時，所需的所有先備認知是否都已在前文被充分交代？
  - [ ] 同一層級的基礎線索是否已經「成批鋪齊」，而非零散斷裂？
  - [ ] 段落之間是否有平滑的因果過渡，而非生硬跳躍？
  - [ ] 讀者的心理模型（Mental Model）是否呈平滑線性或層次生長，而非反覆經歷認知斷崖？

### 3. 短段落切分與「粗類比先行、細節後調」（Chunking & Coarse-to-Fine Analogy）

這條原則承接上一節的「工作記憶負荷」觀點，進一步處理**文章的展開節奏與閱讀顆粒度**：

- **適合**：知識筆記、技術科普、概念導讀，以及任何希望讀者能高效率攝取主線的文章。
- **原則一：控制段落長度，一段只推進一步（Short Chunks）**：
  - 單一段落過長會讓視覺與工作記憶同時過載，讀者容易在中途失焦、忘記這段原本要回答什麼。
  - 每段盡量只承載一個清晰節拍（例如一個核心直覺、一個因果轉折或一個具體例子），適時拆段或輔以條列／小標，給讀者明確的停靠點。
- **原則二：先抽象輪廓，再逐層展開細節（Abstract-First to Minor Details）**：
  - 進入一個新主題時，先在 **abstract level** 把整體在做什麼、各部件怎麼互動勾勒出來，再逐步下鑽到實作細節與邊界條件。
  - 若一開始就陷入細枝末節，讀者缺乏高空地圖，很難判斷眼前這個細節該掛在哪個位置。
- **原則三：允許「夠用就好」的粗類比，細微差異延後微調（Good-Enough Analogy & Deferred Refinement）**：
  - 在建立 abstract level 認知時，優先用生活或熟悉領域的類比把概念形狀立起來。**類比不需要一開始就 100% 精準同構**——重點是讓讀者先快速形成正確的大方向心智模型。
  - 類比與真實機制之間的細微差異，往往在後續深入細節或實際應用時才會真正碰上；**到需要時再回頭校準、微調差異（just-in-time refinement）**，整體學習與閱讀效率會高於「一開始就為了一個比喻補滿十條免責聲明」。
  - **邊界提醒**：這與嚴謹論文／規格書的要求不同——在一般知識筆記中，除非該差異會立刻導致核心誤判，否則不必在引入類比的當下就急著拆穿所有例外；若是撰寫學術報告（見下一節），則仍應保持類比簡短並明確標出適用邊界。

### 4. 學術報告 / 論文寫作檢查清單（Academic Writing Flow）

- **適合**：課程報告、survey、paper 與其他英文學術寫作。Agent 協助撰寫或潤稿時，應先套用這份清單。
- **整體風格**：讀起來要像學生自己寫的，不要有 AI 腔。與其像寶寶一樣大幅刪減，不如補上具體的解釋。
- **檢查清單**：
  1. **第一人稱，講清楚「我們做了什麼」**：例如 "In this project, we survey…"、"We study…"、"We then…"。避免用定義式的句子開頭，像 "X asks how…"。
  2. **每節、每小節開頭都要有過渡句**：交代這一段跟前文的關係，以及為什麼接著講它。例如 "With the benchmark in place, we can ask why…"、"What if we relax neither condition?"
  3. **並列結果先預告**：先寫 "…did so in two ways. The first…"，後面再接 "Their second result…"，不讓第二個結果突然冒出來。
  4. **Introduction 的順序**：具體情境 → 正式概念 → 引導問題 → 章節導覽（roadmap）。
  5. **長證明先預告**：開始前先說明分幾步，以及每一步在做什麼。
  6. **類比要短**：並明講它在哪裡不成立。
  7. **重複的摘要段改成承上啟下**：不要只是把前面講過的再講一遍。
  8. **指代要清楚**："this"、"the same paper"、"the restriction" 這類詞要能明確對應到前文；有歧義就直接寫出名稱。
  9. **順句子的同時核對適用範圍**：潤稿時要檢查每個說法的範圍是否正確（例如曾經發現 "only coverage" 的說法其實不對）。
  10. **改寫時盡量維持篇幅**：改完重新編譯並確認頁數，再用中文說明新增了哪些過渡句。
  11. **過渡句不能預設讀者還沒看過的事實**：例如還沒說明 1/2 和 1−1/e 的差距，就先寫 "why a one-pass algorithm falls behind greedy"。下筆前先問「讀者此刻知道什麼？」，缺的事實先補上，最好能呼應上一節的結尾。
  12. **表格和圖要在需要它的概念之後立刻引入**：說明關鍵欄位怎麼讀；章節導覽放在表格引用之後。
- **參考範例（章節導覽 roadmap）**：

  > The report is organized as follows. Section 2 defines the problem and the offline greedy benchmark. Section 3 surveys the known results, grouped by which assumption each one changes. Section 4 proves the Sieve-Streaming guarantee and compares it with the streaming k-center algorithm from the course. Section 5 discusses the cost hidden in the oracle model and proposes a question about changing objectives.

  這段好在：每一節只用一句話交代「做什麼」，而且帶出組織邏輯（例如 "grouped by which assumption each one changes"），也點出跟課程內容的連結，而不是只列出章節標題。
- **持續擴充**：review 時發現清單還沒涵蓋的毛病，就補進這一節。

## 寫作模板

### 1. 觀點論述型

- 適合：有一個明確主張，想說服讀者接受一個看法或 framing。
  - 範例：個人職涯反思、技術選型哲學、對產業趨勢的獨到見解。
- 讀者狀態：對議題有基本概念，但不知道作者為什麼這樣判斷。
- 典型順序：
  1. 用一個反直覺觀察或 tension 開頭
  2. 先亮主張
  3. 拆 3-5 個 supporting arguments
  4. 插入反例 / 限制條件
  5. 收束成一個更 general 的原則
- 常見失敗：太早講抽象大道理，沒有足夠例子把讀者帶進來。

### 2. 教學拆解型

- 適合：教讀者完成一個流程、理解一個方法、重做一個結果。
  - 範例：手把手搭建 CI/CD 流水線、環境配置指南、新工具 Step-by-Step 實作。
- 讀者狀態：有任務壓力，想快速知道怎麼做。
- 典型順序：
  1. 先講要解的問題與讀完可得到什麼
  2. 前置條件 / prerequisites
  3. 先給最小可行版本
  4. 按步驟遞增複雜度
  5. 補 pitfalls / debugging / edge cases
  6. 結尾給 recap 與延伸方向
- 常見失敗：一上來就貼完整大成品，沒有階段性停靠點。

### 3. 知識型文章 / 方法筆記型

- 適合：整理一個技術主題、演算法、方法論或一組相關概念，讓讀者從「知道名字」走到「理解用途、原理、限制與比較」。
  - 範例：機器學習演算法 (K-Means, DBSCAN)、分散式一致性協議 (Paxos, Raft)、資料探勘核心任務。
- 讀者狀態：對主題可能有初步印象，但需要一篇結構清楚、能快速建立整體心智模型的文章。
- 偏好節奏：先直覺、再抽象、再正式定義。也就是先用生活例子或具體場景把讀者帶進來，再抽象成「這裡真正要定義的是什麼」，最後才落到正式術語、數學目標或演算法假設。
- 典型順序：
  1. Introduction: Why?（背景 / 為什麼值得關心）
  2. Introduction: What?（它是什麼）
  3. Landscape / Branches（如果主題是一個方法家族：有哪些主要路線 / 變體 / 實作分支）
  4. Approach: How?（若本篇主角是單一方法，才在這裡深挖怎麼運作）
  5. Limitation / Trade-offs（單一方法頁優先保留；overview 頁只收斂到家族層級的邊界）
  6. Comparison（例如 `K-Means vs. DBSCAN`；若主題沒有明確對照組，可視情況省略）
  7. Conclusion: Key Takeaways
- 使用建議：
  - 若文章重點是「幫讀者建立一個方法的完整輪廓」，這套結構很穩。
  - 起稿前最好先把 `TLDR / NarrativeArc / Scope` 補出來，確有後續篇目才加 `FollowUps`，再決定這篇是 overview、single-method deep dive，還是 comparison。
  - 若這篇其實在講「方法家族 overview」，正文應優先回答：這類方法在解什麼問題、主要分支有哪些、差異軸是什麼；不要同時把每個方法的 limitation 都展開講完。
  - overview 頁若需要提到代表方法，應該「一筆帶過到足以建立地圖」；不要讓 `K-Means` 或任何單一方法的直覺段落長到吃掉整篇主 flow。
  - 若某個方法的 limitation、tuning、failure mode 已經需要 2-3 個小節，通常代表它值得獨立成一篇。
  - 若文章包含兩個以上方法，`Comparison` 不只是附錄，甚至可以是整篇的核心價值。
  - 若文章只有單一方法、沒有直接對照組，可把 `Comparison` 改寫成 `When to Use / When Not to Use`。
  - 結尾若想雙軌收束：正文可用 `## Summary` 寫一小段段落式總結；條列式重點則另外放進 `<takeaways>`
  - 參考建議規範：主標題採 `## 參考資料（References）`，並視需要分為 `### 學術論文（Academic Literature）` 與 `### 技術文章（Technical Articles）`。學術論文採 APA / IEEE 格式並連至 Abstract 頁面（非 raw PDF），確保專業度與可查證性。
  - 若想在文章前段放導讀 block，優先寫成「TL;DR / Focus / Article Compass」，用來固定主題、scope 與 main flow；不要預設再開一個專門的 `Guiding Questions` block。
  - 若需要插入輔助理解的小元件：`block` 偏摘要卡，適合 quick insight / quick notes；`callout` 偏導讀式補充，適合放直覺、比喻與重要理解方式。
  - 若想先用一個快速 heuristic 判斷：疑問句導向的補充通常更適合 `callout`；重點整理、摘要、結論式的補充通常更適合 `block`。
  - 但要記得：`block` / `callout` 都是正文 flow 之外的 branch，不應喧賓奪主。文章主線本身必須能獨立成立，重要內容應盡量留在主 flow 裡，而不是把關鍵論證都塞進補充元件。
  - 上面這個 heuristic 只是快捷規則，不是硬性分類；真正的最高判準仍然是它是否與主文章 flow 相容。
  - 判斷某一段要留在正文還是抽成 `block` / `callout` 時，優先看它是否與主文章 flow 相容：能推進主線的內容留在正文；有價值但會打斷節奏的內容，再考慮抽成補充元件。
- 常見失敗：
  - `How?` 寫得太細變成 implementation dump，反而失去知識型文章的可讀性。
  - `Limitation` 與 `Comparison` 太晚出現，讓文章看起來像單方面介紹而不是 decision aid。
  - 同一篇既想做 overview，又想完整教完 `K-Means / DBSCAN / Hierarchical Clustering`，結果變成 overloaded survey。
  - 原本想寫 `clustering overview`，最後卻花大量篇幅在 `K-Means` 的直覺與流程，導致文章表面上在講家族，實際上已經偏向單一方法教學。
  - 把單一方法的 limitation 留在 overview 頁，導致節奏從「建立地圖」突然跳成「深入 debug 某個方法」。

### 4. 比較分析型

- 適合：兩種以上選項的 trade-off、策略比較、框架選型。
  - 範例：REST vs. GraphQL vs. gRPC 選型指南、幾何量化 (RQ-Kmeans) vs. 神經量化 (RQ-VAE) 技術比較。
- 讀者狀態：已知道自己要做決策，但不確定判準。
- 典型順序：
  1. 定義比較對象與 decision context
  2. 先給總結表態或判準
  3. 按維度比較，而不是先講完 A 再講完 B
  4. 補適用情境與反例
  5. 最後給 recommendation
- 常見失敗：寫成 feature list，而不是 decision guide。

### 5. 研究 / 讀書摘要型

- 適合：把一堆資料、論文或書籍內容壓成可遷移的 takeaways。
  - 範例：頂會論文研讀導讀、技術書籍精華導讀、產業研究報告整理。
- 讀者狀態：沒空讀原文，但想快速吸收真正值得留下的觀念。
- 典型順序：
  1. 先講這份摘要的篩選口徑
  2. 用 3-6 個主題聚類
  3. 每個主題下固定分成「核心概念 / 泛化應用 / 限制」
  4. 最後總結跨主題共同原則
- 常見失敗：變成逐條抄錄，而沒有抽象出 transferable insight。

### 6. 反思札記型

- 適合：記錄思考轉變、學到什麼、為何改變做法。
  - 範例：專案失敗後的 Post-mortem 檢討、從開發者轉為管理者的心路歷程。
- 讀者狀態：對你的脈絡有興趣，希望看見推理過程，而不只是結論。
- 典型順序：
  1. 先交代觸發事件或原始困惑
  2. 寫原本怎麼想
  3. 寫哪個觀察或經驗讓你改觀
  4. 寫現在的新 framing
  5. 補尚未解決的 open questions
- 常見失敗：只有情緒、沒有可被別人沿用的結論。

### 7. Case Study / How We Built It

- 適合：講一個系統、專案、產品功能是如何被設計與落地。
  - 範例：高併發秒殺系統設計、大規模向量資料庫架構重構。
- 讀者狀態：想知道你怎麼思考與取捨，不只想看成果圖。
- 典型順序：
  1. 問題背景與約束
  2. 為什麼現有做法不夠
  3. 設計原則 / 成功標準
  4. 方案拆解
  5. Trade-offs / 邊界條件
  6. 結果、教訓、後續
- 常見失敗：只講 solution，不講 constraint，所以讀者學不到 decision logic。

### 8. 架構演進與範式重塑型

- 適合：當某個領域正經歷從傳統經典架構向新一代範式轉型，說明為何舊系統觸及工程物理天花板，以及新範式的破局邏輯與核心瓶頸。
  - 範例：從漏斗級聯推薦走向端到端自迴歸生成推薦、從單體架構走向微服務 / Serverless 架構演進。
- 讀者狀態：熟悉經典做法，但想知道舊架構為何撞牆，以及新範式的升維邏輯與優勢。
- 典型順序：
  1. Hook 與經典情境（從極限工程約束切入，交代舊架構歷史紅利）
  2. 舊架構深層痛點（剖析目標錯位、IO 吞噬算力、硬體/GPU 天性不相容等死穴）
  3. 新範式破局之道（說明觀念轉變、統一目標、對齊硬體 Scaling Law）
  4. 核心關鍵瓶頸（點出新範式最大的工程死穴，如海量物品 Token 化）
  5. 技術路線導覽（比較解決瓶頸的兩大/多大技術路線）
  6. 結語與 ReviewKit（總結趨勢，搭配 Key Takeaways 與 References）
- 常見失敗：只講新技術優點，沒把舊架構撞牆的物理/硬體根因講透。

### 9. 演算法與 Tokenizer 階層剖析型

- 適合：深入拆解一個複雜的量化、Tokenizer 或機器學習核心子演算法，說明如何將高維連續空間轉為離散階層 Token，並處理實務落地細節。
  - 範例：RQ-Kmeans 幾何殘差量化、RQ-VAE / VQ-VAE 端到端神經量化、BPE / SentencePiece Tokenizer 機制。
- 讀者狀態：已明白戰略方向，但需要理解演算法的底層幾何/數學原理、梯度傳播與防禦機制。
- 典型順序：
  1. 戰略承接與破題（明確回答演算法需具備的任務：離散化映射 + 階層結構）
  2. 基石鋪陳與直覺陷阱（從生硬網格分桶的維度詛咒切入，引出單層量化 VQ）
  3. 突破單層極限的階層魔法（用地圖縮放/逐層殘差比喻，解釋殘差量化 RQ 的樹狀階層）
  4. 核心幾何/數學與訓練傳播（幾何殘差接力賽或 STE 梯度估算與 Loss 設計）
  5. 深水區：極端挑戰與防禦機制（剖析死碼危機/碼本崩塌 Codebook Collapse 與防禦機制）
  6. 業界落地工作流與架構選型（離線訓練 -> 索引建構 -> 線上推論與務實選型）
  7. 總結與 ReviewKit（收束結論，提供 Key Takeaways 與 References）
- 常見失敗：陷入純數學推導或代碼 dump，忽略了直覺比喻與工業落地的 trade-offs。
## 種子參考文章

下面不是「官方標準答案」，而是一批值得逆向拆結構的 seed examples。重點不是模仿文風，而是學它們怎麼安排讀者的理解節奏。

### 觀點論述 / Essay

- Paul Graham essays：很適合學「反直覺 opening → 主張 → 例子 → 升維結論」的節奏。
- 可先看：
  - `How to Get Startup Ideas`
  - `Do Things That Don't Scale`
  - `Maker's Schedule, Manager's Schedule`

### Engineering / Case Study

- Stripe Engineering：很適合學「背景 → 約束 → 系統設計 → trade-off → result」這種產品/工程寫法。
- Cloudflare / GitHub / Figma / Notion 等工程 blog 也常有高質量的 how-we-built-it 結構，可持續補充到這裡。

### Tutorial / 教學拆解

- 優秀 tutorial 的關鍵不是「內容多」，而是有清楚的最小版本、遞增步驟與 pitfalls 區塊。
- 之後若看到一篇真的把複雜主題講得很順的 tutorial，可以直接在這裡補上 URL 與你拆出的節奏。

## 後續擴充方式

- 若某一種模板開始頻繁重複使用，可以再為它新增：
  - 建議標題公式
  - 建議 opening 類型
  - 建議 section heading 節奏
  - 建議結尾方式
- 若未來決定把其中 1-2 種模板產品化成 `tools/create_content.py` scaffold，再回頭從這份文件抽出「最穩定」的骨架，不要反過來讓實作綁死寫作本身。
