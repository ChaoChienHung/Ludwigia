推薦常先從龐大商品庫召回數千件，再由粗排縮到數百件，最後由精排決定呈現順序。三階段都要讀同一位使用者的歷史，若分別訓練、分別部署模型，長序列便重複編碼。OneTrans-V2 延伸 OneTransNotesOneTrans：同一個 Transformer 如何處理行為序列與特徵交互推薦系統OneTrans...從傳統推薦模型分開處理歷史與特徵的成本出發，拆解 OneTrans 的 S／NS tokens、混合參數、因果遮罩、金字塔序列與快取。，把三階段做成同一 Transformer 的任務，但仍保留「召回 → 粗排 → 精排」的候選縮減流程。原論文

1. 先畫出共用與隔離的邊界

使用者行為序列與候選無關，先編碼成共用的 user context。三階段的 token 各讀取這份脈絡，但階段 token 彼此不可見，行為 token 也不反向讀取候選。於是粗排選中某件商品，精排可拿到入選商品，卻不直接讀取粗排 token 的 hidden state。原論文 §4.1

                ┌→ 召回：生成候選 SID
使用者歷史 → 共用脈絡 ├→ 粗排：少量特徵 → 每件候選 1 個 token
                └→ 精排：完整特徵 → 每件入選候選多個 tokens

粗排的單 token 是少量候選側特徵的壓縮表示，不是商品 PID 本身。精排使用更完整的非序列特徵集，保留多個 token 以免過度壓縮；這些也不保證逐一等於原始欄位。原論文 §4.2.2

2. 三種任務如何共訓？

召回的 DCGR 先預測這次互動的決策前綴，再逐步生成商品的三層 SID。取回實際商品後，粗排與精排分別預測 CTR、CVR 等分數；精排輸出還可在同模型內指導粗排，減少早期淘汰精排原本看好的商品。總訓練目標是召回、兩種排序與蒸餾損失的加權和，不代表三階段使用同一組特徵或同一種輸出。原論文 §4.2

3. SNT 與線上快取：兩種「歷史算一次」

訓練時，Sequence-Native Training（SNT） 將同一使用者在時間窗口內的曝光聚到一條因果行為時間線，編碼歷史一次。每筆曝光保留時間戳、階段特徵與標籤，只能讀請求當時已發生的歷史。這不是把 request 當成新行為插入歷史，而是把曝光錨定到相應歷史前綴。論文相對逐曝光重編碼的基線報告 4.4 倍訓練速度。原論文 §4.4、§7.9

線上一次請求則先建立 user context 的 KV cache，再讓召回、粗排、精排讀同一份快取。因果 attention 保證新行為只追加在後面，不會改寫舊歷史位置的表示；候選側工作仍要按階段執行。論文的 3.2 倍 QPS 是相同硬體預算下、連同服務端優化的整體結果；它不是「每次請求 FLOPs 降為三分之一」的意思。原論文 §5.1、§7.9

4. 如何與其他路線定位？

MTFMNotesMTFM：跨業務共用行為骨幹並擴大 Target 表示推薦系統MTFMMeituan...從美團多場景推薦的特徵不一致與長序列成本出發，理解 H/R/T tokens、動態遮罩、Hybrid Target Attention 與 Target Scale-Up。 主要統一多業務場景的精排；OneTrans-V2 統一同一推薦流水線的三個階段。HSTUNotesHSTU：把推薦改寫為使用者行為的序列預測推薦系統HSTU...從逐候選打分的重複計算出發，理解 HSTU 的序列轉導、pointwise aggregated attention、長序列工程，以及它與後續排序模型的邊界。 則由行為序列預測問題出發。它們都重視使用者歷史與計算重用，但處理的系統邊界不同。

Key Takeaways

  • 共用的是使用者歷史的模型脈絡；三階段的候選側 token、特徵與任務仍不同。
  • 粗排單 token 壓縮少量特徵；精排對入選商品使用多個較豐富的特徵 token。
  • SNT 在訓練窗口內跨曝光共用歷史；線上在單次請求內跨階段共用快取。
  • 召回生成 SID，排序預測分數；共訓不等於三階段執行完全相同的運算。
