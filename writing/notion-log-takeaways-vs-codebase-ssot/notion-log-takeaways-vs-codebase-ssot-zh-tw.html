為什麼在 Agent 時代，我越來越不想用 Notion 記錄 codebase

我最近越來越強烈地感覺到一件事：在現在這種 agent 幫忙讀 code、改 code、理解 code 的 workflow 裡，Notion 裡最值得留下來的，好像不是 codebase 本身，而是日誌、takeaways，還有那些比較不會頻繁變動的重點。

  • 我現在其實有在寫專案日誌
  • 但越寫越覺得，真正需要在 Notion 裡維護的內容，可能只剩這一層
  • 反而那些「目前 codebase 長什麼樣」、「這個模組現在怎麼串」之類的記錄，常常剛寫完沒多久就過期了

這讓我開始懷疑：在 Agent 時代，我們是不是不該再把 Notion 當成 codebase 的平行鏡像？

Setup：記錄的本質到底是什麼

我現在對「記錄」的理解越來越偏向這個方向：

  • 記錄是為了保存重要資訊，避免未來遺忘、重工、或重走同一段思路
  • 如果某個資訊在未來高度不穩定、很快就會失效，那它被記錄下來的價值本來就會下降
  • 換句話說，真正值得記錄的，通常不是那些一直在變的表層狀態，而是比較穩定的脈絡、理由與結論

所以問題不只是「我能不能把 codebase 記下來」，而是：

  • 這些記錄未來還有沒有價值？
  • 它們的維護成本跟回報到底成不成比例？
  • 如果之後最有效率的理解方式仍然是直接讀 code，那我為什麼還要維護一份次級描述？

Code 在 Agent 協作下，越來越像真正的 SSOT

在過去，記錄 codebase 的一個很大理由，是理解 code 的成本高。

  • 人要自己翻檔案、自己追呼叫鏈、自己補上下文
  • 所以把某些結構先整理到 Notion，確實能降低協作者的理解門檻
  • 那時候「文件作為快速入口」的價值很高

但現在狀況不太一樣了。

  • Agent 讀 code 的速度比人快太多
  • Agent 最擅長的事情之一，就是直接從 code 裡抽出結構、責任邊界與資料流
  • 如果要理解現在的系統，最直接的方法其實還是去讀 code，而不是讀某份可能晚了一版的整理文件

在這種情況下，code 的 single source of truth 地位反而更明顯了。

  • 因為 code 才是實際執行的東西
  • 因為 code 變動時，Agent 可以直接重新解讀最新狀態
  • 因為任何平行維護的 codebase 摘要，都很容易在高頻修改下失真

為什麼 Notion 裡的 codebase 摘要越來越像高成本低回報

這裡最麻煩的不是「記錄做不到」，而是「維護它變得不值得」。

  • 現在 code 的變動頻率比以前高很多
  • vibe coding / agentic AI 讓重構與快速嘗試的門檻大幅降低
  • 結果是：很多你今天寫下來的架構描述，過幾天就過期了

這會帶來一個很尷尬的情況：

  • 你花很多時間整理 Notion
  • 但未來真的要理解系統時，還是得回去看 code
  • 那份 Notion 若沒跟上最新狀態，甚至還可能誤導自己

所以我越來越覺得，對 codebase 做這種高頻同步，會慢慢失去「記錄」的本心。

  • 記錄原本是為了防止遺忘
  • 但如果某個資訊一直變，表示它可能本來就不適合被當成長期知識保存
  • 它更像是 execution state，而不是值得長期沉澱的認知資產

以前我們需要小模型，現在越來越像直接在本體上工作

我最近還想到一個更具體的比喻。

以前如果要蓋一棟大樓，我們很可能會先做一個小模型。

  • 小模型讓大家比較容易討論
  • 新人可以先看模型理解整體結構
  • 要改哪一層、哪一面，也可以先在模型上模擬

在那個脈絡下，Notion 裡的 codebase 文件就很像那個小模型。

  • 它不是本體
  • 但它是一個方便討論、方便理解、方便協作的縮影

可是在 Agent 出現之後，整件事慢慢變了。

  • 我們不太需要花很多時間手工維護那個小模型
  • 因為 Agent 可以直接去讀本體
  • 它甚至可以直接把修改先作用在本體上，再快速回報結果給你

這時候再去維護一份平行的小模型，反而開始顯得很瑣碎。

  • 它沒有以前那種「完整專案感」
  • 它也不再是理解系統最有效率的入口
  • 很多時候，直接在本體上討論、直接在 code 上改，反而更快

如果這個比喻成立，那就代表：

  • 在 Agent 時代，codebase mirror 的必要性下降了
  • 我們剩下真正需要額外記錄的，主要是那些「沒辦法直接在本體上出現的東西」

例如：

  • 當時為什麼這樣決策
  • 我們捨棄了哪些方向
  • 哪些 takeaways 值得之後重用
  • 哪些觀察現在還只是暫時假設

這些東西才是就算把整份 code 再讀一遍，也不一定能高效率取回來的部分。

那 Notion 還適合記什麼

我現在比較認同的方向是：Notion 不要再試圖複製 codebase，而是專心記錄 code 之外、更不容易直接從 code 讀出的東西。

目前我最認同的幾類是：

  • 專案日誌：今天做了什麼、遇到什麼問題、為什麼轉向
  • Takeaways：這次實作後留下來的穩定結論
  • 決策理由：為什麼選 A 不選 B，當時的 trade-off 是什麼
  • 待驗證觀察：某些還沒完全定論，但值得後續回頭檢查的假設

這些東西有一個共同點：

  • 它們不是 code 的直接鏡像
  • 它們也不是靠重新讀 code 就能最有效率地取回
  • 它們保存的是「當時的上下文與判斷」，而不只是「現在檔案裡長什麼樣」

也許最合理的配置是：日誌 + takeaways，而不是 codebase mirror

如果只保留專案日誌，我覺得已經很有價值。

  • 它保留了時間序
  • 它保留了決策與卡點
  • 它讓之後回頭看時，不需要重新拼湊「那時候到底在想什麼」

但如果再往前一步，我覺得還可以加一個更精煉的層：

  • 日誌負責保存過程
  • takeaways 頁負責保存沉澱後仍然有效的重點

這樣的分工也許比「維護一整份 codebase overview」更有意義。

  • 日誌回答的是：這段時間發生了什麼
  • takeaways 回答的是：從這些變動裡，哪些結論值得留下
  • code 則維持為真正的 SSOT：如果要理解當前系統，回去看 code 即可

這背後其實不是 anti-documentation，而是重新定義什麼值得被記錄

我現在不是覺得文件不重要，而是越來越覺得，文件應該集中在那些不容易被 code 取代的資訊。

  • 如果某件事重新讀 code 就能拿回來，那它未必值得在 Notion 裡再維護一份
  • 如果某件事的價值來自上下文、判斷、路徑依賴，那它才更值得被記錄
  • 在 Agent 時代，理解 codebase 的成本下降了；所以文件的角色也應該跟著改變

也許最後最合理的結論不是「不要記錄」，而是：

  • 不要再花大量力氣同步記錄那些會高頻變動的 codebase 表象
  • 把 Notion 留給日誌、takeaways、決策理由、以及真正不想遺忘的脈絡
  • 讓 code 做最擅長的事：成為最新、最準的 single source of truth

也許我真正想保留的，不是 code 的快照，而是成長的痕跡

如果這個想法成立，那我之後在 Notion 裡最該維護的，可能真的不是「這個 repo 現在怎麼長」，而是：

  • 我最近在做什麼
  • 我學到了什麼
  • 哪些結論下次還用得到
  • 哪些東西只是短期 execution state，不值得投入心力長期同步

這也許才比較接近記錄真正的意義。

  • 不是複製一份會過期的系統說明
  • 而是留下那些未來的我真的會感謝現在的我有寫下來的東西
