我最近越來越覺得，寫作 workflow 本身也正在被 Agent 改寫。

以前比較常見的流程是：

  • 我先自己把每一段都寫得差不多完整
  • 再回頭修文、重排、補例子
  • 如果中途發現結構不夠好，就得把很多段落整個打散重寫

但現在我越來越偏向另一種順序：

  • 先定清楚文章架構
  • 再把每段需要回答的問題列出來
  • 然後把 raw info 丟給 Agent / LLM 幫我補內容
  • 最後再做一次全盤 proofread

我不是在說「讓 Agent 取代寫作」，而是：

  • 先把最重要的結構與問題意識抓穩
  • 再把填充內容、整理措辭、補例子這些工作盡量交給工具加速
  • 但最後的人類 proofread 仍然是整個流程裡最重要的一環

為什麼我現在更偏向架構先行

如果文章還沒有結構，很多時候真正卡住的不是文字本身，而是：

  • 這篇到底想回答什麼
  • 哪些段落應該先講
  • 哪些只是補充、哪些才是主軸
  • 哪些疑問其實還沒被釐清

在這種情況下，直接把段落一股腦寫滿，常常只是比較早暴露混亂，而不是更接近成稿。

所以我現在更喜歡先做一個比較明確的骨架。

  • 先列大章節
  • 每個章節再列它要回答的核心問題
  • 如果有需要，再把每節拆成更小的子段落

做到這一步，其實文章已經開始變得很好 refine 了。

因為這時候你不是在面對一整團模糊的「我要寫一篇文章」，而是在面對很多個相對清楚的小任務：

  • 這段要不要補例子
  • 那段是不是還缺反例
  • 哪一節的過渡不夠順
  • 哪個 claim 目前還太空

架構一旦清楚，raw info 就更好交給 Agent 處理

我覺得這一步是 Agent 真正開始有價值的地方。

如果你只有一團散亂的想法，Agent 雖然也能幫忙，但很容易：

  • 寫得很滿，卻沒有真的對準問題
  • 產生過度 generic 的段落
  • 把還沒想清楚的東西直接包裝成看起來完整的文字

但如果你已經先把架構和每段問題列出來，狀況會不一樣。

你可以直接給它：

  • 這一節的標題
  • 這一節想回答的問題
  • 你目前手上的 raw info
  • 你想保留的語氣、立場、限制

這樣 Agent 的工作就不是「憑空替你寫一篇文章」，而是：

  • 依照既有結構補足內容
  • 把 raw info 組織成比較可讀的段落
  • 在必要時用 prior knowledge 幫你補上說明、例子或比較

這種協作方式會讓文章比較不容易失焦。

生成之後，還可以反過來用結構再 refine 一輪

我很喜歡這個 workflow 的地方在於，它不是單向的。

不是說：

  • 先做 outline
  • 然後 Agent 補完
  • 就直接結束

而是：

  • 先用 outline 把文章拆清楚
  • 再用 Agent 把各段補起來
  • 接著把生成後的內容重新攤回結構上看

這時候你會更容易看到：

  • 哪些段落太空
  • 哪些段落太長
  • 哪些段落其實在重複
  • 哪些子問題應該被拆出去

也就是說，文章一旦同時有了「架構」和「暫時的內容」，refine 反而會變得更容易。

因為你現在不是在 refine 一片空白，而是在 refine 一個已經有輪廓的東西。

這種 workflow 其實讓很多前置工作都可以被簡化

我現在的感覺是：

  • 在 proofread 之前，其實很多步驟都可以被簡化或 agent 化

例如：

  • 收斂大綱
  • 幫每節列子問題
  • 整理 raw info
  • 生成第一版段落
  • 把長段落拆短
  • 補對比、例子、反例
  • 把結構反向列成一份 refine checklist

這些工作很重要，但它們不一定都需要由我親手從零完成。

真正不能被省略的是最後那輪全面性的閱讀。

最後的全盤 proofread，反而是最不能省的一步

這是我現在最確定的一個結論。

前面的流程可以優化、可以加速、可以部分委派給 Agent。

但最後還是要有一輪完整 proofread。

因為只有在你從頭到尾把整篇文章當成一個整體重新讀過時，你才會真正看見：

  • 語氣是不是一致
  • 過渡是不是自然
  • 立場是不是被寫歪了
  • 某些句子是不是雖然通順，卻不是你真正想說的
  • 某些段落是不是看起來完整，但其實沒有回答問題

這一層目前很難完全外包。

不是因為 Agent 不會改文，而是因為最後這一步在做的事情不是「補文字」，而是：

  • 對整篇文章的意圖負責
  • 對邏輯一致性負責
  • 對語氣與判斷負責

這也是為什麼我會覺得：

  • 前面的流程都可以簡化優化
  • 但 proofread 一定要留到最後，並且由人完整走過一遍

我現在比較想採用的實際流程

如果把整件事寫成一個比較實用的 workflow，我目前偏好的是：

  1. 先寫文章架構
  2. 幫每個段落列出要回答的問題
  3. 把 raw info、例子、觀察、碎念全部先丟進對應段落
  4. 讓 Agent 依架構補成第一版可讀內容
  5. 把生成後的內容重新映回結構，列出 refine 點
  6. 再做一到兩輪定向修改
  7. 最後做一次全盤 proofread

這個流程對我來說最大的好處是：

  • 不用在一開始就承擔「我要一次把整篇寫對」的壓力
  • 可以把高成本的填充工作交給 Agent
  • 同時又不會放棄對整篇文章的最終掌控

結論：不是把寫作交出去，而是把寫作拆成更適合協作的層次

我現在越來越不把這種 workflow 理解成「讓 Agent 幫我寫文章」。

更像是：

  • 我先定義結構與問題
  • Agent 幫我把內容快速補起來
  • 我再回來做最後的判斷與 proofread

也就是說，真正被外包出去的，主要是那些可被系統化、可被填充、可被重組的部分。

真正被保留下來的，是：

  • 架構判斷
  • 文章立場
  • refine 的方向
  • 最後的整體 proofread

對我來說，這不是偷懶。

反而比較像是把寫作這件事重新拆對層次之後，讓每一層都交給最適合的人或工具來做。
